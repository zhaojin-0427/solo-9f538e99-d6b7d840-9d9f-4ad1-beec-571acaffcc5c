# 生鲜到货数仓入库排查

采购员和商品档案员共用的排查网页：把 **到货**、**采购行**、**用码记录** 三种 CSV
分批上传进 SQLite，逐笔判定到货能否进数仓，并按「阻断原因 + 采购行号 / 条码」
分别给出两边各自的待修清单、受阻笔数和逐笔明细。

## 阻断规则

一笔到货只有在**零阻断**时才放行。

| 侧 | 原因码 | 中文 | 判定 |
|---|---|---|---|
| 采购/档案侧（按采购行号） | `purchase_line_missing` | 采购行缺失 | 到货的采购行号在采购行表中不存在 |
| 采购/档案侧（按采购行号） | `barcode_mismatch` | 条码不符 | 扫码条码 ≠ 该采购行的约定条码 |
| 用码/档案侧（按条码） | `barcode_unowned` | 到货时该码无归属 | 没有任何用码记录的区间覆盖到货时刻 |
| 用码/档案侧（按条码） | `barcode_ambiguous` | 该码对应多种商品 | 覆盖到货时刻的用码记录涉及不止一种商品 |

* 用码期 **含起点、不含终点**：`starts_at <= arrived_at < ends_at`。
* 一笔到货可同时挂在两张清单上（两侧都违规）；同一侧至多一条原因
  （采购行缺失/不符互斥；无归属/多商品互斥）。
* 放行状态 = 当前阻断原因条数为 0。任一原因再次出现即退回受阻。

## 上传与更正语义

* 三种 CSV 各自上传；**同类同号以本次上传为准**（编号即业务主键，
  到货=`编号`，采购行=`采购行号`，用码记录=`编号`），同文件内重复编号以最后一行为准。
* 一次上传 = 一个 SQLite 事务：底表 upsert → 只回查**受影响**的到货 →
  重算其阻断原因 → 写批次审计 → 提交。
  * 到货上传：回查文件内编号对应的到货（含更正后换了采购行/条码的）。
  * 采购行更正：回查所有使用该采购行号的到货（改动前、改动后取并集）。
  * 用码记录更正：回查所有使用该条码的到货（改动前条码 ∪ 改动后条码）。
* 任意一环节失败 → 整体回滚，**底表、清单、放行状态全部保留上次结果**；
  失败仅作为一条 `failed` 批次记录出现在审计列表里（不参与结果）。
* 清单里的「受阻笔数」直接由阻断原因明细聚合，与明细逐条一致。

## CSV 格式

表头可用中文或英文（大小写、空格、`-_/` 忽略），编码支持 UTF-8（含 BOM）与
GB18030，分隔符支持逗号 / 分号 / 制表符。

| 类型 | 列 |
|---|---|
| 到货 | `编号`、`采购行号`、`扫码条码`、`UTC 时刻` |
| 采购行 | `编号`（采购行号）、`约定条码` |
| 用码记录 | `编号`、`条码`、`商品`、`UTC 起`、`UTC 止` |

UTC 时刻接受 ISO-8601（`Z` 或 `+08:00` 等偏移，归一为 UTC 存储）。
全部文件先整批校验再入库：任一行不合法（缺值、时间不可解析、止早于起）
整批拒绝，不产生半批数据。

示例见 `samples/`：`purchase_lines.csv`、`scan_records.csv`、`arrivals.csv`
（含放行、条码不符、采购行缺失、无归属、多商品、区间边界各一例）。

## 页面

| 路径 | 用途 |
|---|---|
| `/` | 上传（可先「仅预检」）、到货总数/受阻/放行、按原因受阻笔数、最近批次（含失败原因） |
| `/worklist` | 采购侧（按采购行号）与用码侧（按条码）两张待修清单，按原因分组，含受阻笔数与逐笔明细 |
| `/arrivals?q=` | 到货查询（编号 / 采购行号 / 条码），显示当前放行状态 |
| `/arrivals/<编号>` | 单笔到货：当前是否放行、全部阻断原因、采购约定条码、覆盖该时刻的用码记录 |
| `/review` | 入仓时限复盘：按首次成功上传的 UTC 日期，逐日统计到点时仅采购侧 / 仅用码侧 / 两侧均受阻的笔数 |

## 入仓时限复盘（`/review`）

补档负责人用来比较不同入仓时限下，超时到货集中卡在哪一侧。

* **输入**：UTC 起始/截止日期（含首尾，最多 31 天）与 1～120 的整数分钟时限。
* **逐日口径**：按到货编号**首次成功上传**的 UTC 日期归组；只纳入复盘功能
  **启用后首次出现**的到货编号；只列出**日末已满两小时**的日期（未成熟日期
  跳过并在页面注明）。
* **计时**：以成功批次**开始写入时的 UTC 时刻**（`upload_batches.received_at`）
  为起点，时限 = 首次成功上传时刻 + N 分钟。到点时刻**含等号**：恰好到点的更正
  算在内；同一时刻有多个批次时按提交顺序（批次 id 大者）取最后状态。
* **四档计数**：到货总笔数，以及到点时仅采购侧受阻、仅用码侧受阻、两侧均受阻；
  到点时已放行的计入总笔数但不进任何受阻档。
* **同批生效、失败沿用原数**：底表 upsert、阻断原因重算与复盘时间线在同一个
  SQLite 事务内提交；失败整批回滚，复盘数字保持上次结果（失败只进批次审计）。
  时间线持久化在库内，重启后接着累计。
* **稀疏写入**：每个批次只为「本批新增」或「阻断侧集合发生变化」的到货追加一行
  侧别状态（掩码 0/1/2/3），不按分钟逐项写入；阻断侧没变的到货不重复写。
* **统计只读汇总表**：查询只访问 `arrival_first_seen` / `arrival_side_states` /
  `app_meta`，不碰底表；每个日期一条聚合语句，逐笔判定全部在 SQL 内完成，
  单条语句返回给应用的记录数硬上限 24（实际为 1 行日聚合），因此到货总量不会被截断。

复盘功能的启用时刻记录在 `app_meta.review_enabled_at`：在旧库上首次启动新版本时
自动迁移，库内已有到货的「首次出现」被回填为早于启用时刻，从而不进复盘口径。

## 启动

```bash
docker compose up --build
# 打开 http://localhost:8000
```

数据落在命名卷 `freshcheck-data`（容器内 `/data/freshcheck.db`），重建容器不丢数据。
`FRESHCHECK_SECRET` 用于 flash 消息签名，生产请改掉。

本地不带 Docker 运行：

```bash
python3 -m pip install -r requirements.txt
FRESHCHECK_DB=./data/freshcheck.db python3 -m freshcheck
# 或：FRESHCHECK_DB=... gunicorn --bind 0.0.0.0:8000 freshcheck.app:app
```

## 结构

```
freshcheck/
  app.py       Flask 路由
  service.py   上传/更正事务、受影响到货回查、清单与概览查询
  review.py    入仓时限复盘：侧别时间线维护与逐日到点聚合（只读汇总表）
  rules.py     阻断判定与阻断原因缓存重算
  csvio.py     CSV 解析、表头别名、行校验、时间归一
  db.py        连接、schema、迁移、事务、add_minutes SQL 函数
  sqlutil.py   IN (...) 参数分块
  templates/   页面
  static/      样式
tests/         服务层 + Web 层 + 复盘层测试
samples/       示例 CSV
```

## 已知缺项 / 后续可做

* **无页面内手工补录**：补录与更正均通过重新上传 CSV 完成（符合“同类同号以本次
  上传为准”），没有单行编辑表单、下载错误行、或仅上传差异行的功能。
* **预检只报首个错误行**：下载/导出错误明细、一次列全所有非法行尚未实现。
* **无鉴权与角色区分**：采购员与档案员看到同一套清单，未做登录/权限或按角色过滤。
* **无删除语义**：CSV 只能新增或覆盖，无法通过上传“作废/删除”某条采购行或用码记录；
  如需撤销只能上传修正值。
* **单实例 SQLite**：WAL 下多 gunicorn worker 可用，但没有跨主机部署与外部数据库支持；
  列表页未分页，十万级以上到货时 `/arrivals` 会一次性渲染（服务层已按库索引查询，
  5000 行级别实测上传 + 全量回查在 0.2 秒内）。
* **时区**：仅接受带偏移或裸时刻（按 UTC 解释），不做按门店时区的本地化展示。
